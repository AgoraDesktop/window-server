# window-server

**Agora's window server** — a Wayland compositor, and the program every Agora application's windows are shown
by.

Agora is an installable desktop environment for Linux and BSD; see the project README in the parent directory
(`../README.md`). This is the bottom of the desktop: above it are the AppKit, and the applications.

## System menu identity

The server detects the running OS once, at startup, and resolves it to an exact mark: Debian, Ubuntu, Linux Mint,
Fedora, Red Hat, Arch, openSUSE, Alpine, FreeBSD, OpenBSD, NetBSD, or DragonFly BSD. **DragonFlyBSD uses the FreeBSD
mark for now**; there is no separate DragonFly artwork in this set. A derivative without its own mark inherits its
`ID_LIKE` family's mark (Kali gets Debian, Rocky gets Red Hat, Manjaro gets Arch); anything unmatched gets the
hamburger.

The marks are monochrome vector paths, rasterized once into a 16×16 coverage grid and blended by the compositor. The
hamburger is original and CC0 1.0; the exact OS marks come from Simple Icons and remain the trademarks of their
projects. See `assets/system-menu-icons/PROVENANCE.md`.

```
$ ./build/window-server --dump-os-identity
sysname: Linux
source: /etc/os-release
ID: debian
ID_LIKE: (none)
NAME: Debian GNU/Linux
family: debian
system menu icon: debian

$ ./build/window-server --list-system-menu-icons
$ ./build/window-server --system-menu-icon mint ...   # force one, for a test or a look
```

The detection ladder is `/etc/os-release`, `/usr/lib/os-release`, `/etc/lsb-release`, the per-distro release files,
then `uname` for the platform family. The data lives in `assets/system-menu-icons/`; the C tables are generated by
`tools/gen-icon-table.py`. See `SYSTEM-MENU-ICON-PLAN.md` for the rest.

## Status

**The first version works: it accepts clients, gives them surfaces, composites what they draw, and screenshots
it.** The two acceptance tests below hold it up; the unit suite covers the smaller rules, including the System menu
marks.

### 1. The AppKit renders into it

`libagora-app`'s `NSWindow` — a real window, a real `NSView` overriding `-drawRect:`, pumped through
`NSApplication` — pointed at **this** compositor instead of at mutter:

```

$ WAYLAND_DISPLAY=awsrun1 libagora-app/build/tests/appkit_window --seconds 1

window-server: 90 frame(s) composited
window-server: wrote /tmp/agora-ws.ppm

$ python3 ../libagora-app/tests/inspect.py /tmp/agora-ws.ppm
red marker   : 2304 px at (40,62)..(87,109)      (48x48, the window's top-left)
green marker : 2304 px at (632,414)..(679,461)   (48x48, its bottom-right)
window on screen: 640x400 at (40,62)

  [ok] both markers are square                  [ok] gradient R rises left to right (36 -> 198)
```

That is the whole stack: a view's `-drawRect:`, through `NSWindow`, through the seam, into **Agora's own

### 2. And it runs nested, in a window on a desktop

`--backend x11` puts the compositor's screen in an X window — the same thing weston's `--backend=x11` and
mutter's `--nested` are. An independent capture of the desktop, with the AppKit client running inside it:

```
$ ./build/window-server --backend x11 --frames 200 --screenshot /tmp/ws-x11.ppm

$ python3 ../libagora-app/tests/inspect.py /tmp/ws-x11.ppm      # the compositor's own output
  [ok] red marker is the top-left corner   [ok] green marker is the bottom-right corner
  [ok] both markers are square             [ok] gradient R rises left to right (36 -> 215)
  [ok] gradient G rises top to bottom      [ok] a white bar is present

$ python3 ... # on an X screenshot taken at the same time
  red marker on the desktop  : 2304 px at (360,277)..(407,324)
  green marker on the desktop: 2304 px at (952,629)..(999,676)
  -> a 640x400 window at (360,277), red top-left, green bottom-right
  the nested window's own corner (320,237) is (48,51,56) — the window server's background
```

**IT GRABS NOTHING, AND THAT IS NOT AN ACCIDENT OF THE CODE YET.** This server has no input devices (no
`libinput`, see below), so the backend presents pixels and takes no input: no `XGrabPointer`, no
`XGrabKeyboard`, no pointer fence. That matters because a nested compositor *with* input can leave a desktop
with a dead mouse — which is a real failure this project has already met once, from a nested `gnome-shell`.
A compositor that has nothing to route has nothing to grab, and that stays true until input arrives on purpose.

**An X11 backend is not an X11 target.** Agora's display target is Wayland on real hardware, with Xwayland for
X *clients*; this is a development backend, which is why it is **optional** — the core links no `libX11` at all
unless it is built in (`-DWITH_X11` is not needed: it is taken if `pkg-config` finds it).

### 2a. Two renderers, and the GPU one is proved nested

Compositing is not the backend's job: `--renderer` chooses who draws the scene, and the composite **order**
(levels, the menu bar, which surfaces cast shadows) lives once in `aws_output_walk` so two renderers cannot
disagree about it.

```
$ ./build/window-server --backend x11 --renderer gl --frames 200 --screenshot /tmp/ws-gl.ppm
window-server: gl renderer: EGL 1.5, NVIDIA GeForce GTX 1060 6GB/PCIe/SSE2
```

- **`cpu`** is the original compositor, moved verbatim to `src/renderer-cpu.c`. Every backend can run it.
- **`gl`** is EGL + GLES2 (`src/renderer-gl.c`). Shadows and rounded corners are the same distance function and the
  same constants as the CPU path, in a shader.
- **`auto`** (the default) takes `gl` when a backend hands it a native window — today only the nested X11 backend —
  and falls to `cpu` otherwise. A renderer **asked for by name** that cannot start is a hard failure, not a silent
  fallback.

**THE NESTED OUTPUT IS WHERE THE GPU RENDERER WAS BUILT, AND THAT IS THE ARGUMENT RATHER THAN A CONVENIENCE.**
Acceleration is two independent halves: the renderer, and the display path that gets a finished frame onto the
glass. Nested X11 exercises the first with no DRM master, no KMS driver, no virtual terminal and no logind seat,
and on this machine it is the only place the first half is testable end to end: the DRM path is proven to the
dry run (see §5) and not to the picture. A DRM accelerated path is therefore a GBM swapchain added **under** this renderer,
not a second renderer beside it.

**AND THE TWO RENDERERS ARE CHECKED AGAINST EACH OTHER, NOT AGAINST A FEELING.** Both answer `--screenshot`; the GL
one reads its frame back with `glReadPixels` before it swaps. A CPU frame and a GL frame of the same scene differ
in **at most 2 of 255 per channel, and only on shadow falloff edges** (float blend against integer division); every
window, corner, bar and menu pixel is identical. That measurement is what caught a real bug: the shadow shader was
sampling from pixel centres, painting a dark line at row 24 where the CPU painted nothing.

**WHAT THIS DOES NOT ACCELERATE YET, recorded rather than left to be found.** Client buffers are `wl_shm` and are
uploaded as textures every frame, so this makes *composition* cheap, not *client painting* — the AppKit still draws
on the CPU. The next win is `zwp_linux_dmabuf_v1` import on both sides of the wire, and that is a separate piece of
work.

### 2b. GPU buffers: `zwp_linux_dmabuf_v1`

A `wl_shm` window is CPU memory the compositor uploads every frame — 5.8 MB per frame for a 1600x900 window. A
dma-buf window is a file descriptor the GPU samples where the client put it, so the upload disappears.

```
$ ./build/window-server --backend x11 --renderer gl &   # advertises the (format, modifier) pairs it can import
$ WAYLAND_DISPLAY=... window-server-test-client --dmabuf
window-server: dmabuf: 81 (format, modifier) pair(s) advertised
```

- **Advertised only when the active renderer can import.** `aws_dmabuf_init` runs *after* the renderer and asks it
  for the formats its EGL context can sample; `--renderer cpu` advertises nothing, so a client is never promised a
  buffer that would be dropped.
- **Bound at v3.** v4's `zwp_linux_dmabuf_feedback_v1` answers "which device and which modifiers are fast" — a
  multi-GPU question. One GPU has one answer, so the flat `format`/`modifier` list is the honest advertisement;
  clients that know v4 fall back to it.
- **Single-plane RGB only.** NV12 would need a colour-conversion pass this renderer does not have.
- **`external_only` matters, and it is measured.** NVIDIA reports LINEAR XRGB8888 as `external_only`, which means the
  EGLImage can be bound to `GL_TEXTURE_EXTERNAL_OES` and *not* to `GL_TEXTURE_2D` — MEASURED, as
  `GL_INVALID_OPERATION` out of `glEGLImageTargetTexture2DOES`. The renderer therefore has two texture programs and
  picks by the driver's answer, per buffer.

**THE TEST IS A PIXEL COMPARISON, NOT AN ASSERTION THAT IT RAN.** `tests/run-dmabuf.sh` photographs the same window
once through shared memory and once through a dma-buf and fails on a single differing pixel; it skips (77) on a
machine with no display or no render node.

**AND WHAT IT DOES NOT FIX.** It removes the compositor's upload. It does not make the AppKit paint on the GPU — that
is the client half, and until it exists dmabuf buys the server side only.

### 2c. When a buffer is released, and why it is not a per-frame question

`wl_buffer.release` is a **promise that the compositor will not read those pixels again**, so the client is
entitled to repaint them the instant it arrives. This server used to send it from its frame sweep while keeping
the buffer as the surface's content: every composite after the release read memory a client had already begun to
overwrite. **MEASURED, as the blink on a focus change** — capture the nested output at 60 Hz and click from one
window to another: one frame in the middle of the repaint changed 62% of a window's pixels and put *both* windows
half-drawn on the glass, for about a tenth of a second. The repaint is not slow; it was being photographed.

The release now happens where the compositor's claim ends — in `surface_commit`, on the commit that REPLACES the
buffer (or the one that detaches it) — and a composite never releases anything. The other half of the fix is on
the client: a window has **two buffers** and paints into the one that is not on the glass, so a repaint is never
done in place on pixels the screen is showing. Neither half is enough alone (see the note at the top of
`libagora-app/platform/AGWindowServer-Wayland.c`).

That makes two obligations for anything else that speaks to this compositor:

- a client that wants to paint while its last frame is still displayed needs a second buffer, because the first is
  held until it is replaced;
- a client's **partial** paints have to account for the buffer they land in being one frame behind — AppKit widens a
  damage rectangle to what that buffer is missing (`_cg_paintMissing` in `NSWindow.h`), and a client that ignored
  this would leave stale strips behind.

### 3. Input travels the whole way

The seat is driven by the nested backend, and the input was sent STRAIGHT TO THE WINDOW (`XSendEvent`) rather
than by moving the real pointer — a synthetic pointer lands on whatever the window manager stacked on top, and
on a busy desktop that is not this window. An AppKit client on the other end:

```
window: pointer entered at 260,160     the injected motion, in SURFACE coordinates (300,200 less the
window: key 30 down text="a"           window's cascade at 40,40)
window: key 30 up text="a"
```

The keycode that went in was the X keycode 38; the client saw evdev **30** and translated it to `"a"` through
the keymap this compositor sent it. That is the whole chain: X keycode → evdev → compositor → `wl_keyboard` →
the client's own xkbcommon.

**THE FOCUS POLICY IS TWO HALVES AND BOTH ARE NEEDED**: a window takes the keyboard when it is MAPPED, so a
person can type into the first thing that appears, and a CLICK moves it. The first half was missing and it
showed: keys arrived with the focus nil and went nowhere.

### 3a. What a click costs, measured in three places

A session driven by hand felt sluggish — a click answering about a second late — and the fix was in the
compositor, not in the client. Instrumenting the three processes with one wall clock (the client's event, the
client's paint, the server's render and present) gave this chain for one click, at 1600x900, with a wallpaper
client committing frames:

| stage | before | after |
|---|---|---|
| shadow around a full-screen surface | 10 ms | 0.5 ms |
| composite of one surface | 10-20 ms | 1-2 ms |
| full render (clear + surfaces + bar) | 30 ms | 5-7 ms |
| present (XPutImage) | 4-9 ms | 2-4 ms (XShm + one round trip) |
| **click, press to pixels** | **150-1000 ms** | **60-90 ms** |

The first row was a ring drawn as a rectangle: `aws_output_draw_shadow` walked the shadow's whole expanded
rectangle and asked for a square root per pixel, so a desktop-sized window paid 1.4 million of them a frame.
It now walks the ring — a row that crosses the frame paints its two side bands, a row outside it paints the
whole width.

The second row was the same mistake in the composite: `shape_coverage` was asked once per pixel for a number
that is 255 for every pixel that is not within the corner radius of a corner. A row clear of both corner bands
is now a COPY when the surface is opaque (no alpha to blend, and `XRGB8888`'s `X` is not alpha) and a
zero-skip-and-blend when it is transparent (a desktop icon window is mostly nothing, so four pixels are asked
at once). Only the corner bands still ask for a shape.

The last row is a development backend's own cost: `XPutImage` sent 5.8 MB of pixels over the X connection for
every frame. The backend now asks for MIT-SHM and draws straight into a segment the X server has already
attached, so a present is a pointer and a `XSync` — the sync is deliberate, because the segment is drawn into
again on the next frame and the server must have finished reading this one. A server without the extension
falls back to the copy, because a compositor that refused to run on a remote X display would be worse than one
that is slow on it.

**AND THE CLIENT'S HALF WAS FIXED THE SAME DAY, WHICH IS WHAT BROUGHT THE LAST ROWS DOWN**: a click repainted the whole
file window — every string and every icon — because the damage rectangle never became a CLIP, the compositor's frame
callback answered with a whole-frame paint, and `-orderFront:` marked a window that was already on screen stale on
every activation. With those three fixed a click paints its two cells: **3.6-10.8 ms**, against 20-45 ms for the whole
window. See `libagora-app/README.md`'s "Damage" section and `APPKIT_DRAW_DIAG`, which prints the rectangle and the
milliseconds of every paint.

### 4. libinput: written, built, and blocked by a permission

`--input libinput` is implemented, links, assigns **seat0** successfully through logind — and then cannot open
a single device. libinput's own log handler (which is production code a compositor wants anyway; without one it
fails in silence) says exactly why:

```
libinput: event0: opening input device '/dev/input/event0' failed (Permission denied).
libinput: event0  - failed to create input device '/dev/input/event0'
... (every device)
window-server: libinput could not be started; falling back
```

**The measured cause, in two parts, and the first is the one that matters:**

```
$ loginctl list-sessions
SESSION  UID USER SEAT  LEADER CLASS   TTY
      1 1000 kyle -     1391   manager -        <- this process's session: NO SEAT
      3 1000 kyle seat0 2191   user    tty2     <- the graphical session

$ getfacl /dev/input/event0
user::rw-          group::rw-          other::---      (owner root, group `input`; no ACL for kyle)
```

logind grants a session's devices to processes **in that session on that seat**, and this one runs in a
`manager` session with no seat — so nothing is granted. And the devices are `root:input` with no user ACL, so
there is no second way in. **`sudo usermod -aG input kyle` (then log out and back in) is what unblocks it**;
the group `rw` is already there, and nothing else has to change.

Notice what is NOT wrong: udev finds the devices, libinput builds them, and the seat assignment succeeds. The
failure is one `open()` and it is the operating system's answer rather than the compositor's.

### 5. DRM/KMS: written, proven to the modeset on this machine, not yet composited on glass by its author

`--backend drm` is the shipping backend: it opens a card, takes DRM master, allocates **two dumb buffers**, maps
them, and points a CRTC at them through an atomic commit — no copy, no GBM, no EGL. Frames are written straight
into the buffer that is not being scanned, and the swap is a flip at vblank (`flip_pending` holds the loop off the
page the display may still be reading).

**WHAT IS MEASURED HERE VERSUS WHAT IS CLAIMED.** `AWS_DRM_DRY_RUN=1` takes the device, picks the connector, mode,
CRTC and plane, allocates both buffers and both framebuffers and the mode blob, and gives master back without
setting anything: that passes on this machine with `nvidia_drm.modeset=1`. A *committed* modeset has not been
replayed by this file's author since the HiDPI and virtual-terminal work landed, so the picture on glass is
unverified — see §6 for the terminal machinery that must be right before anyone tries it on a machine they cannot
reach over SSH.

**Two things it must do that a windowed backend never does**, and both are safety rather than features:

- **It takes DRM master**, the kernel's one-claimant lock on the device. An X server or another compositor
  holding it makes this FAIL and say so — which is what makes the backend safe to start by accident: a
  compositor cannot quietly take a display away from the session using it.
- **It puts the previous mode back on the way out**, so leaving is not a screen left in a state only a reboot
  fixes.

**IT DOUBLE-BUFFERS AND FLIPS AT VBLANK, WHICH IS WHAT PAGES ARE** — one buffer is scanned while the compositor
draws into the other, and the new one is handed over at the next vblank, so the display never shows a frame that
is half drawn. **AND THE FLIP IS ASYNCHRONOUS**: the render loop asks the backend `busy` before it draws, and `busy` answers yes
until the flip event has been read off the DRM descriptor, which is on the event loop. So the wait is real but it
is spent in the event loop, where the rest of the compositor keeps working — not inside `present`, where nothing
could. That also paces the compositor to the display's refresh rather than to how fast it can paint.

**THE ATOMIC REPLACEMENT IS NOT YET CONFIRMED ON A SCREEN.** The legacy path was measured
to be inert on this driver (see below) and has been replaced by `drmModeAtomicCommit`. Everything up to the
commit is verified by the dry run; **the commit itself has not been run**, because its failure mode is the
display of the person running it.

**AND THE CLAIM BELOW WAS MADE ONCE WITHOUT BEING CHECKED, AND WAS WRONG** — the numbers are what the
COMPOSITOR did, not evidence that light came out of a monitor, which is a thing only a person looking at the
screen can say:

```
$ ./build/window-server --backend drm --frames 120 &
$ WAYLAND_DISPLAY=… libagora-app/build/tests/appkit_window --seconds 4
window-server: driving /dev/dri/card0 at 1920x1080 (dumb buffer scanout)
window-server: 120 frame(s) composited
appkit_window: drew 120 frame(s); frame now 640x422
server exit=0
$ xdpyinfo | grep dimensions   ->  3840x1080      (the desktop is back on both monitors)
```

`AWS_DRM_DRY_RUN=1` RUNS EVERY STEP UP TO THE MODESET AND STOPS, which is how the setup path above was proven
before anything was allowed to touch a screen:

```
  connector  77 (DVI-D), 11 mode(s)
  mode       1920x1080 (PREFERRED)
  crtc       42
  buffer     1920x1080, pitch 7680, 8294400 bytes, mapped at 0x…
  framebuffer 93 (XRGB8888)
  Master was taken and is given back; nothing was set on the CRTC.
```

**THE LEGACY PATH IS ACCEPTED AND DOES NOT DISPLAY, WHICH IS WHY THE BACKEND IS ATOMIC NOW.** `drmModeSetCrtc`
returns 0 and `drmModeGetCrtc` then reports this framebuffer on this CRTC — and no monitor changes. The
driver's own state says why:

```
connector 77: CONNECTED, encoder_id=0      encoder 76: crtc_id=0
connector 79: CONNECTED, encoder_id=0      encoder 78: crtc_id=0
CRTCs: 42 52 62 72 — every CRTC reports no framebuffer
```

Nothing is bound to anything in the legacy model, and a desktop is nonetheless on the screen: the live path is
**atomic modesetting**, and the legacy ioctls are only being recorded. A test that filled a dumb buffer with
solid red, held it for eight seconds and called `drmModeDirtyFB` produced NO CHANGE ON ANY MONITOR, which is
what settled it.

`drmModeAtomicCommit` is what this backend does now: the connector's `CRTC_ID`, the CRTC's `MODE_ID` blob and
`ACTIVE`, and the primary plane's `FB_ID`/`CRTC_ID`/`SRC`/`CRTC` rectangles, committed with `ALLOW_MODESET` —
plus `drmModeDirtyFB` in `present`, because a driver has to be TOLD the memory it is scanning has changed or it
shows one frame and never another. The dry run reports all of it:

```
connector   77 (DVI-D), 11 mode(s)      mode  1920x1080 (PREFERRED)      crtc  42
plane       36 (PRIMARY)                framebuffer 92 (XRGB8888), mode blob 94
```

**AND THE ONE OBSTACLE ON THIS MACHINE IS THE DRIVER, NOT THE CODE**: X holds the GPU through the proprietary
NVIDIA driver's own interface, so a DRM/KMS modeset has nothing to take. The evidence is in X's log —
`(II) NVIDIA(0): NVIDIA GPU GeForce GTX 1060 6GB` and a validated MetaMode for both DFP outputs — which is why
`drmSetMaster` succeeds, why the legacy state shows nothing bound, and why an accepted atomic commit changes no
pixel. **Verifying this backend therefore needs a display nobody else is driving**: a text VT with the display
manager stopped. `Ctrl+C` is then the way out, and it runs the teardown because signals stop the event loop
rather than killing the process.

**RELEASING THE DISPLAY IS PART OF THE MODESET AND HAS THE SAME RISK.** On the way out the CRTC is turned off
and the connector detached — before the framebuffer and the buffer under it are destroyed, because a CRTC still
scanning them out makes that destruction wrong. If X is not the DRM master (and on this machine it is not, which
is why `drmSetMaster` succeeds), it may not re-assert afterwards, and the way back is a VT switch.

**MEASURED, AND A MACHINE WITH NO KMS SAYS SO:**

```
$ ./build/window-server --backend drm
window-server: /dev/dri/card0 has no KMS resources at all. On a machine with the proprietary NVIDIA
                driver this is KMS being OFF IN THE KERNEL: `nvidia_drm.modeset=1` ...
exit=1

$ ls /sys/class/drm/card0-DP-* | wc -l     -> 0     (no connectors, no CRTCs)
```

The card can render and cannot display, which is the proprietary NVIDIA driver's default. There is no `vkms`
virtual-KMS module on this machine to test against either. So the backend is built, links, enumerates, and
**refuses with the reason** — and the paths to making it testable are `nvidia_drm.modeset=1` (a kernel module
parameter plus an initramfs rebuild and a reboot) or installing `vkms`.

### 5a. A point is 1/72 inch, so the scale comes from the panel

The output has two sizes: `width x height` is the framebuffer in **device pixels**, and the **logical** screen is
what clients are told about. The scale is the number between them — device pixels per logical point — and its
default is not a threshold guess at 1x or 2x. It is derived from the display's own physical size, because a point
is a physical unit:

```
    dpi   = pixels_wide * 25.4 / millimetres_wide
    scale = dpi / 72
```

A 24" 1080p monitor (1920 px across 531 mm) is 91.8 dpi, so its scale is 1.276; a 13" 4K laptop panel (3840 px
across 294 mm) is 331.8 dpi, so its scale is 4.61. Both show a menu bar of the same physical height and text of
the same physical size; the dense panel simply has more pixels to draw it with. The same rule runs the **nested
X11 backend** against the host screen's millimetres, so a nested session is the physical size it would be natively,
and the **DRM backend** against the connector's reported active width.

**EDID IS NOT BELIEVED BLINDLY.** A connector that reports no millimetres, a width under 50 mm, or a dots-per-inch
outside 50–400 says nothing usable — a wrong scale resizes every window on the screen — so the answer is "no answer"
and the scale stays 1. `--scale N` still overrides the derivation entirely, which is the escape hatch for a monitor
with a corrupt size block.

**AND A CLIENT STILL HEARS AN INTEGER.** `wl_output.scale` is an integer in the protocol, so `aws_output_scale_integer`
rounds up: a 1.28x output is advertised as 2, the client renders at 2x, and the compositor downsamples 2 -> 1.28.
That is what makes a fractional scale sharp instead of a magnifying glass. `headless` has no panel to ask, so it
stays at 1 unless `--scale` says otherwise.

The arithmetic and its guards are `src/scale.c`, and `tests/scale.c` asks them directly — no display required.

### 6. It is tested without the AppKit

`ctest` — the server, a client that is nothing but the protocol, and a check that reads the server's own
screenshot:

```
  [ok] the output is 1280x720
  [ok] the client's colour is at the cascade (40,40)
  [ok] the window is 320x200
  [ok] nothing of the client is outside it
  [ok] and the rest is the compositor's own background
check: 5 checks, 0 failed -- all checks passed
```

The server does **not** depend on `libagora-app` — the dependency runs the other way — so its own test uses
`tests/client.c`, the smallest thing that is a real Wayland client.

## What this version deliberately does not do

Each of these is recorded at the code that would have to change (`src/server.h`), because an absent feature
that is written down is a decision and one that is not is a surprise.

- **Three backends, and the shipping one cannot be tested on every machine.** `headless` is a framebuffer in
  this process, `x11` is a nested window on an X server, and `drm` drives a real display through Kernel Mode
  Setting. The first two run anywhere; the third needs a KMS device, and see below for what happens when there
  is not one. A backend is a place to put pixels — a width, a height and a buffer — which is what makes a new
  one a file (`src/backend-*.c`) rather than a change to the compositor.
- **Input has two sources and the OUTPUT does not decide which.** `--input libinput` reads the machine's own
  devices through udev and logind; `--input host` takes the events the nested backend's window is given. They
  are mutually exclusive — both feed one seat, and a device read twice is a pointer that moves at double speed
  — and the default is libinput when it can start, the nested window otherwise. See below for the one thing
  that still blocks libinput on this machine.
- **No cursor.** `wl_pointer.set_cursor` is accepted and does nothing: a nested output's pointer is the HOST's,
  and a second cursor drawn into the window is one the person did not ask for.
- **No drawing of its own.** The menu bar, the status area and the window frames are the window server's to
  draw in a Mac-like desktop, and this owns none of them yet — which is the honest reason there is no drawing
  library in the build. The compositing is a row copy. **Who owns which pixels, and why `xdg-shell` cannot
  express it, is written down in [`DESIGN.md`](DESIGN.md)** — including Apple's own window-level names, which is
  the evidence that the menu bar is stitched from windows owned by different processes.
- **No policy — AND IT NO LONGER CASCADES.** A cascade was a placement policy, and the Mac's model is that the
  application states its frame and the server honours it; that cascade is gone. What remains absent is anything
  that would place a window the application did not, and the furniture the server owns beyond a menu bar's
  reserve. **The server's half of that model is implemented: `agora_shell`** — see `protocol/agora-shell.xml`
  and [`DESIGN.md`](DESIGN.md).

## Build and run

```sh
cmake -S . -B build -DCMAKE_C_COMPILER=clang
cmake --build build
cd build && ctest

# run it, and point a client at it
./build/window-server --socket agora &
WAYLAND_DISPLAY=agora some-wayland-client
```

Two system libraries, neither vendored: `wayland-server` (the protocol, the event loop and the shared-memory
buffer plumbing, which libwayland owns through `wl_display_init_shm`) and `xkbcommon` (the keymap a seat
sends). The xdg-shell bindings are **generated** at build time from the system's `wayland-protocols`, so a
checked-in copy cannot silently age against the protocol on the machine.

## The architecture this is being built toward

Three owners of the screen — a compositor with system-owned furniture, applications, and the Dock as an
application of its own. The Dock is **not written here**, but the two things it needs from this side are: a
LEVEL (`kCGDockWindowLevel`, an integer like any other) and a RESERVED REGION. The second is
`agora_window.set_reserved` — a client says how many pixels along which edge are its own, the work area is the
output minus the menu bar minus every such strip, and `agora_output.work_area` is re-sent to every client when the
sum changes. `tests/work_area.c` is the proof, and it is a probe rather than a screenshot because a reservation
moves no pixels. **And a window may say that clicking it must not activate its application**
(`set_activatable`) — the Dock needs it, because a Dock that took the keyboard would take the menu bar with it;
`tests/window_list.c` asserts that such a window gives the keyboard back and refuses `activate_window`. See
[`DESIGN.md`](DESIGN.md).

**WHAT A DOCK ASKS, AND WHAT IT CAN DO ABOUT THE ANSWER, IS NOW THE PROTOCOL'S OWN.** `get_window_list` is the
snapshot a shell draws from (and the one thing an ordinary application never asks for), `activate_window` and
`close_window` are the click and the Quit, and `reopen_window` is the click that has nothing to raise — the
application is asked to show a window and decides what that means. `tests/window_list.c` is the proof of all four,
because it is a shell and two applications in one process, which is the only way to write those assertions without
a race. **And the other side of the same question is `agora_window.take_focus`**: an application saying "this one of
MINE is key", which is `-makeKeyWindow` — focus without a raise, and only ever about a window the caller owns.
Without it a window opened by a click that had nothing to raise came forward with the keyboard left behind.

**AND A TILE'S MENU IS A ROUND TRIP, BECAUSE THE PANEL AND THE ITEMS HAVE TWO OWNERS.** A right-click on a tile shows
what the application offers for that tile with the Dock's own rows under them — one panel, and the application
cannot draw in it. So `get_dock_menu` asks an application for its dock menu and `agora_dock_menu.menu` carries the
answer back to the client that asked (that object exists precisely so the answer has an address: a window id says
nothing about who asked); `dock_menu_action` sends the chosen item's id home, and `agora_window.set_dock_menu` is the
application's answer. **This server never parses a menu** — the description is the AppKit's at both ends, and a
compositor with an opinion about items would be the same mistake a special case for "the dock" would be. An ask it
cannot deliver (a window that has gone, or a client bound below version 6) is answered EMPTY NOW rather than left for
a timeout to say later. `tests/window_list.c` asserts the whole round trip, including both of those answers.

**THE SHELL GLOBAL IS AT VERSION 6.** Version 3 added the window list and the two requests on somebody else's
window, 4 carried `set_activatable`, 5 added `reopen_window` and `take_focus`, and 6 is the tile's menu — four
requests and two events, and no change to how windows are placed.

What is still absent on this side, named rather than left to be discovered: no minimized state, no session (so
nothing emits `close` on shutdown), and no cross-process data device — which is what a drop on the Dock's Trash
icon needs.

### 6. Claiming a terminal, and how to undo it

**STATUS: UNTESTED ON GLASS.** Everything in this section is implemented, builds, and is covered only as far as its
refusals and its unit tests go — **no claimed terminal has been composited on by a DRM backend**. The first attempt
stranded a session (see the deadline and the deferred arming below, which exist because of it). Someone else is testing
it and will report back; until that report exists, treat `--launcher vt` as experimental and do not run it where you
cannot recover over SSH.

`--launcher vt --vt N` switches to terminal `N` and takes it: `VT_ACTIVATE` + `VT_WAITACTIVE`, then `setsid` +
`TIOCSCTTY` so that terminal is this process's controlling one, and — once the first frame has been composited —
`VT_SETMODE(VT_PROCESS)` so that every later switch is a question the kernel asks this process (`SIGUSR1`, answered
with `VT_RELDISP`).

**THE TERMINAL IS NAMED AND NEVER CHOSEN.** `VT_OPENQRY` is deliberately unused: on a machine with a display manager
"the first free terminal" is a getty's, and a compositor that takes it moves a person off their session and onto a login
prompt. That is not a hypothetical — it happened, on the machine this was developed on, and it is why `--vt` is
required and why `--vt-timeout` exists.

**A CLAIM HAS A DEADLINE.** `--frames N` counts *composited* frames, so a claimed terminal with no client composites
none and never reaches its own exit condition; `--vt-timeout` (default 10s) gives the terminal back and exits when
nothing has been drawn by then. The negotiation is armed only after the first frame, so a compositor that never gets
that far never takes the keyboard's switches hostage.

**IF A TERMINAL IS STRANDED ANYWAY** — a `VT_PROCESS` owner that was killed, stuck, or rebooted mid-session leaves
**every** terminal on the machine unswitchable, which looks like a dead keyboard. It does not need a reboot:

```sh
sudo python3 - <<'PY'
import fcntl, os, struct
fd = os.open('/dev/tty0', os.O_RDWR)
fcntl.ioctl(fd, 0x5602, struct.pack('BBhhh', 0, 0, 0, 0, 0))   # VT_SETMODE -> VT_AUTO
PY
```

Run from another machine over SSH, or from a shell that still works. `sudo systemctl restart display-manager` afterwards
if a session was left mid-switch.
